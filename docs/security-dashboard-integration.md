# 보안·거버넌스 화면과 후속 작업

## 이번 구현

`/security`에서 `order-svc` 예시를 표시한다. 로그인은 기존 콘솔을 사용한다. 보안 화면 자체는 API를 호출하지 않으며 어떤 환경에서도 예시라는 안내를 표시한다.

| 영역      | 제공하는 정보·동작                                                   |
| --------- | -------------------------------------------------------------------- |
| 상단      | 현재 검토 단계, 보완할 항목, 검사 건수, 다음 동작                    |
| 연결 맵   | 앱 → DB·Redis·오브젝트 스토리지, 연결에 사용하는 계정, 리소스별 결과 |
| 상세      | 보안 조건, 원본 설정, 대상 설정, Redis 권한 변경안                   |
| 검사 근거 | 예시 검사 항목과 향후 수집 위치. 실제 증거가 아님을 명시             |
| 검토 기록 | 이번 시연에서 누른 조사·변경·재검증·승인 기록                        |

흐름: **조사 시작 → Redis 권한 보완 1건 → 변경안 확인 → 적용 후 재검증 → 12건 통과 → 전환 승인**. 변경안을 취소할 수 있고, ‘처음으로’로 시연을 초기화한다. 리소스 네 개를 선택해 각각의 조건 세 개를 볼 수 있다. 한국어·영어·일본어 및 밝은/어두운 테마를 지원한다.

검사 범위는 앱 실행 계정·접근 경로·시크릿 분리, DB/Redis 접근 범위·네트워크·TLS, 오브젝트 공개 접근·경로 권한·HTTPS다. 예시 검사 12건 통과를 전체 보안 인증이나 규정 준수 판정으로 확대하지 않는다. 저장 암호화, 백업·보존, 호스트 패치, 키 관리 등은 이번 시연의 검사 범위에 포함하지 않았다.

## 실제로 동작시키려면

| 우선순위 | 담당                      | 필요한 구현                                                                                                           | 화면에 전달할 결과                                          |
| -------- | ------------------------- | --------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| P0       | control-plane + 수집 작업 | 기존 앱 인벤토리와 연결 계정을 식별. 클라우드 수집기(Prowler 등)의 구조화된 결과에서 해당 앱 리소스만 추출            | 앱·리소스·연결 ID, 원본 설정, 수집 시각, 수집 성공/실패     |
| P0       | IaC / Ansible             | Compose 정적 검사와 대상 호스트의 읽기 전용 사전 조사. 포트 공개, 사용자, ACL, TLS, 객체 정책 확인                    | 선언한 설정과 실제 실행 설정을 구분한 대상 증거             |
| P0       | control-plane 판정기      | 서로 다른 제품의 정책 문법을 ‘누가 무엇에 어떤 작업을 할 수 있는가’ 같은 제한된 조건으로 비교                         | 조건별 pass/fail/unknown, 차이, 근거 참조, 영향받는 연결    |
| P0       | IaC / Ansible + Redis     | 검토 가능한 설정 diff를 만들고 승인된 버전을 적용. 기존 인증은 보존하고 Redis 권한을 제한. 실패/부분 적용 결과를 수집 | plan ID·revision, 변경 내용, 적용 작업 ID·상태·오류         |
| P0       | 검증 작업                 | 적용 후 설정 재조회와 허용/차단 연결 테스트. 세션 키 접근은 성공, 다른 키·금지 명령은 거부되는지 확인                 | 같은 설정 revision에 대한 검증 결과, 실행 시각, 테스트 근거 |
| P0       | control-plane             | 사용자 권한 검사, 승인 저장, 실제 트래픽 전환 직전 서버 측 gate 강제                                                  | 승인자·시각·대상 revision, 전환 가능 여부와 차단 사유       |
| P1       | frontend                  | 실제 앱/마이그레이션 선택, query/mutation, 작업 상태 갱신, 로딩·빈 결과·권한 부족·부분 실패·오래된 증거 화면 연결     | 이 예시 reducer와 타이머를 제거한 운영 화면                 |

프런트가 직접 클라우드 CLI나 Ansible을 실행하지 않는다. 수집 작업을 서버에서 한 번 실행하고 구조화된 결과를 저장한다. 화면은 저장된 결과와 작업 상태를 조회한다. 기존 프로바이더 정책을 온프레미스로 그대로 복사하지 않는다. 이번에 선택한 보호 조건을 호스트·컨테이너·서비스 설정으로 대응시키고, 실제로 유지되는지 검사한다.

Compose의 `ports`가 없다는 사실만으로 네트워크 격리가 입증되지는 않는다. 호스트 라우팅·방화벽과 허용/차단 경로를 함께 확인해야 한다. `secrets` 파일 연결도 자체적인 비밀 저장소나 저장 암호화를 보장하지 않는다. 호스트의 권한·보관·배포 방법은 별도로 검사한다. 화면 fixture의 근거 문자열은 수집 구현의 출발점이며 검증 로직 자체가 아니다.

## API가 제공해야 할 최소 데이터

아래는 **합의가 필요한 계약 제안**이다. 아직 존재하는 endpoint나 백엔드 구현을 뜻하지 않는다.

```ts
type Assessment = {
  id: string;
  workspaceId: string;
  appId: string;
  migrationId: string;
  revision: string;
  collectedAt: string;
  resources: { id: string; type: string; name: string; source: string; target: string }[];
  connections: { from: string; to: string; principal: string }[];
  checks: {
    id: string;
    resourceId: string;
    connectionId?: string;
    condition: string;
    required: boolean;
    source: string;
    target: string;
    status: "pass" | "fail" | "unknown";
    evidenceIds: string[];
  }[];
  gate: { allowed: boolean; reasons: string[] };
};
```

별도 응답으로 증거(수집 도구, 시각, revision, 비밀을 제거한 결과), 변경안(diff, 영향 범위, 적용 작업), 검증 결과, 감사 이벤트를 제공한다. 증거의 만료 기준도 서버에서 정한다. 스캔 요청·조회, 변경안 생성·조회, 적용 요청·상태, 재검증 요청·상태, 승인 요청이 필요하다. 경로·스키마·CSRF·멱등 키는 백엔드와 확정한 뒤 연결한다.

- 서버 오류나 조회 권한 부족을 통과로 표시하지 않는다. 필수 조건이 unknown이면 승인을 막는다.
- 적용 요청 성공은 검증 성공이 아니다. 검증 완료 전까지 gap을 유지한다.
- 승인에 사용한 assessment·plan·configuration revision이 바뀌면 승인을 무효화한다.
- 승인자·시각은 인증된 서버 기록을 사용한다. 브라우저 시계나 reducer를 승인 근거로 사용하지 않는다.
- 승인 여부와 실제 트래픽 전환은 별도 동작이다. 프런트 버튼을 우회해도 서버가 gate를 검사해야 한다.
- 토큰·비밀번호·전체 DSN·개인 키는 응답·diff·로그에 포함하지 않는다. 이름과 secret reference만 전달한다.
- Axios 공통 인스턴스, Zod 응답 검증, workspace/app/migration이 포함된 TanStack Query key와 AbortSignal을 사용한다. 명령 mutation은 자동 재시도하지 않는다.

## AI를 붙일 위치

이번 화면에는 AI 호출이나 빈 채팅 상자를 넣지 않았다. 이후 선택한 gap의 구조화된 조건·원본/대상 값·비밀을 제거한 증거를 AI에 제공해 짧은 설명과 변경안 초안을 만들 수 있다. 답변은 근거 ID를 인용하고, 근거가 없으면 확인이 필요하다고 표시해야 한다.

AI 출력은 `설명`과 `제안`이다. pass/fail 판정, 승인, 설정 적용 권한을 주지 않는다. 설정 초안은 지원하는 Ansible 변수·템플릿 스키마로 검증하고 사람이 diff를 확인한 뒤 실행 작업에 전달한다. 모델·프롬프트 버전과 근거 참조를 함께 기록한다.

## 실행과 변경 위치

```sh
vp install --frozen-lockfile
VITE_API_MODE=demo vp dev --host 127.0.0.1 --port 4210
```

`/security`에서 ‘데모 계정으로 시작’으로 진입한다. `VITE_API_MODE=demo`일 때만 기존 Axios mock을 설치한다. 기본값 `real`에서는 기존 인증/API를 그대로 사용한다. 보안 예시는 브라우저 내 메모리에만 있으며 새로고침하면 초기화된다.

이번 데모는 보안 화면 검토용이다. 승인 후 마이그레이션 목록은 빈 목록이며, 보안 화면의 승인으로 workflow를 생성하지 않는다. 기존 앱 등록·배포의 전체 데모 API는 이번 범위에 포함하지 않는다.

- `src/pages/security/model/demo.ts`: 명시적 fixture, 단계 전환과 검사 건수
- `src/pages/security/ui/`: 요약, 연결 맵, 상세, 증거, 기록
- `src/app/router.tsx`, `widgets/platform-shell`: route·내비게이션
- `src/shared/lib/stack-icons`: 기존 마이그레이션 stack icon을 공유
- `src/shared/lib/i18n/messages.ts`: 화면 문구 3개 언어

실제 연동 시 demo 모드를 요청 결과의 fallback으로 사용하지 않는다. 고정 `order-svc`, fixture 결과, 시뮬레이션 타이머와 승인 reducer를 실제 서버 계약으로 교체해야 한다.
