# AWS → GCP 보안 비교 화면

`/security`는 컨트롤 플레인의 보안 비교 API에 연결한다. 예전 브라우저 reducer와 가짜 조사 타이머를 제거했다. 한 앱의 선택 정책과 두 버킷 직접 권한을 비교하며, 앱의 실제 버킷은 변경하지 않는다.

| 화면      | 표시 정보                                                                 |
| --------- | ------------------------------------------------------------------------- |
| 요약      | 앱 이름, AWS → GCP, 검사 3건, 설정 차이, 대상 앱 준비 응답, 다음 동작     |
| 연결 맵   | 앱 → DB·Redis·오브젝트. 이번 권한 검사는 오브젝트만, DB·Redis는 검사 제외 |
| 상세      | AWS 기준 정책, 앱 버킷 접근 유지, 추가 버킷 접근, GCP 앱 계정             |
| 변경안    | 제거할 데모 버킷/역할과 유지할 앱 버킷/역할                               |
| 검사 근거 | 조회 API, 역할·정책·버킷, 수집 시각                                       |
| 검토 기록 | 서버가 저장한 작업·사용자·시각                                            |
| 목록 버튼 | 설정 재확인과 앱 준비가 성공한 뒤 활성화. 기존 마이그레이션 목록으로 이동 |

흐름은 **권한 조회 → 버킷 권한 차이 발견 → 변경안 확인 → GCP에 적용 → 재검사 → 마이그레이션 목록**이다. 적용만 성공하면 계속할 수 없다. 검사 3건을 전체 보안 검증이나 클라우드 간 실효 권한 동등성으로 표현하지 않는다. 앱 준비 응답은 객체 읽기/쓰기 테스트가 아니다.

## API 계약

- `GET /v1/security-review`: 저장된 결과 조회.
- `POST /v1/security-review/{scan|plan|apply|verify}`: 현재 `revision`, apply만 `planId` 추가.
- 응답: `application`, `mode`, `phase`, `revision`, `source`, `target`, `checks`, `appReady`, `collectedAt`, `verifiedAt`, `validUntil`, `plan`, `events`, `error`, `uiCanContinue`.
- 기존 공통 Axios와 인증/CSRF를 사용한다. 조회는 AbortSignal을 전달하며, 변경 요청은 자동 재시도하지 않는다.
- Zod가 응답을 검사한다. 1.5초 작업 중 조회/15초 상태 갱신을 사용한다. workspace별 query cache를 분리한다.
- UI는 서버의 `uiCanContinue`, verified 상태, 모든 검사 pass, 앱 정상, 만료 시각을 함께 확인한다. 새 조회 오류가 있으면 목록 버튼을 비활성화한다.
- 사용자 브라우저는 대상 계정·버킷·정책을 변경 요청에 포함하지 않는다. 서버 설정 allowlist와 revision/plan/etag 검사가 적용 범위를 제한한다.

**실제 workflow·gate·approval·traffic 전환은 수정하지 않았다.** 이 화면의 목록 버튼만 제어한다. 전체 IAM, 상속 권한, DB·Redis, 온프레미스 보안은 이번 구현 범위가 아니다. AI 호출은 없다.

## 실행

컨트롤 플레인의 `docs/security-review.md`에 ECS 설정, 필요한 클라우드 권한과 로컬 fixture 실행 명령이 있다. 로컬 API를 8112 포트에 실행한 뒤:

```sh
VITE_API_MODE=real CONTROL_PLANE_PROXY_TARGET=http://127.0.0.1:8112 vp dev --host 127.0.0.1 --port 4212
```

`/security`로 접속한다. fixture는 예시 데이터라고 표시하며 실제 API/판정/기록 경로를 거친다. 브라우저 새로고침은 결과를 유지한다. 메모리 API 서버를 재시작하면 예시가 초기화된다. `VITE_API_MODE=demo`의 기존 브라우저 mock에는 이 보안 API를 추가하지 않았으며, 연결 오류를 예시 통과로 대체하지 않는다.

## 배포 연결

1. 백엔드 기능 포함 이미지와 프런트를 배포한다.
2. ECS에 `CONTROL_PLANE_SECURITY_REVIEW_CONFIG_JSON`으로 앱·버킷·허용 사용자를 지정한다.
3. ECS task role에 지정 AWS 역할의 `iam:GetRolePolicy`, 선택한 자격 증명 전달 방식에 필요한 권한을 설정한다.
4. GCP 런타임 계정은 앱 버킷 IAM 조회와 별도 데모 버킷 IAM 조회만 할 수 있게 설정한다. 적용은 별도 계정과 Secret으로 연결하며 그 계정은 데모 버킷 IAM만 관리한다.
5. 컨트롤 플레인 네트워크에서 GCP 앱 `/readyz`와 클라우드 API를 확인한다.

기능이 미설정이면 연결 필요를 표시하며, 기존 앱 등록·배포·마이그레이션은 그대로 동작한다. 화면 검증은 `design-director`의 기존 스타일 유지, 접근성, 좁은 화면 점검을 따른다.

## AI를 붙일 위치

선택한 차이의 구조화된 조건, 원본/대상 값, 비밀을 제거한 증거만 AI에 제공한다. AI는 근거를 인용한 짧은 설명과 변경안 초안을 만든다. 근거가 없으면 미확인으로 남긴다. 판정·설정 적용·전환 승인 권한은 부여하지 않는다. 스키마 검증과 사람이 확인할 diff를 거쳐 기존 실행 API에 연결한다.

## 조회 전용 연결

응답의 `readOnly`가 true이거나 필드가 없으면 조회 전용으로 표시한다. 이 모드에서는 권한 조회와 검사 근거·작업 기록, 변경안 미리보기까지 제공하고 적용 버튼은 비활성화한다. 기존 마이그레이션 화면과 승인 절차는 그대로다. 서버도 적용을 거부한다.

## 적용 동작

운영 설정이 `readOnly: false`이면 차이 발견 → 변경안 확인 → 추가 권한 제거 → 재검사로 진행한다. 확인 창에 계정·제거할 데모 버킷·역할·유지할 앱 버킷을 표시한다. 만료되었거나 조회 오류가 있는 변경안은 적용하지 않는다. 실제 적용 여부와 쓰기 범위는 서버가 검증한다. 조회 전용에서도 변경안을 볼 수 있지만 적용 계정 연결이 필요하다고 표시한다.

실패·작업 중·적용 직후에는 이전 통과 항목을 미확인으로 표시하고 마지막 수집 시각을 남긴다. 공개 사용자 권한이 있는 정책은 서버에서 미확인으로 판정한다. 적용 후 재검사에서 차이 해소와 앱 준비 응답을 확인한다.

## 운영자 화면

- **AWS → GCP**의 오브젝트 상세에는 정책과 별도로 앱의 시험 영수증 읽기, 업무 외 버킷 목록 조회, 복사 계정 읽기를 표시한다. 확인 가능한 경우 조사 시점의 활성 workflow와 객체 migration ID를 함께 표시한다. 미연결, 미확인, 허용, 거부를 구분한다. 기존 GCP 변경안 확인창에서만 데모 버킷 적용을 요청한다.
- **온프렘 샌드박스**의 실행 근거 표는 동일한 세 요청에 대해 기존 설정과 변경 설정을 나란히 보여준다. 복사 시험은 실제 합성 객체 복사와 내용 대조다. 운영자가 설정 diff, 후보 생성 방식, 시험 결과를 확인한 뒤 승인하거나 보류한다. 승인 시 변경 패치와 복구 패치를 내려받아 운영 배포 절차로 넘긴다.
- 서버 revision과 만료 시각을 사용한다. 시험 중, 만료, 실패, 재조회 오류에서는 승인할 수 없다. 새로고침 후에도 서버의 결정 기록을 읽는다. GCP fixture 표시와 실제 SeaweedFS 시험은 독립적이다. 데이터 면 실측·샌드박스·모델 연결은 컨트롤 플레인의 `docs/security-review.md`를 따른다.
